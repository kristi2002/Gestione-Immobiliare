row you clicked. Now navigates to that property's `property_profile` with its real id
(`views/dashboard.html`, `renderRecentProps`/`bindSpaLinks`). Verified by reading the

## 2. Topbar/filter-bar merge on scroll

**Already fixed** by the branch-tip commit before this session started (`f4e2f1b`).
`setupMergeToTopbar` in `filters.js` now portals the *actual* toolbar DOM node

proprietari. **Not re-verified visually this session** (see "Could NOT verify").

## 3. Scheda inquilini

**Built.** New `tenant_profile` view mirroring the proprietari pattern: hero (avatar,
status, contacts, current lease), tabs Locazione/Contratti/Pagamenti/Documenti/
Promemoria, a right-hand rail on row-click with "Visualizza Completo", and a 3-dot
azioni menu (Visualizzazione completa / Modifica / Invia WhatsApp / Archivia)
replacing the old single edit-pencil button. Two small backend gaps had to be closed
to make the tabs real instead of empty: `contracts.php` and `reminders.php` had no
`tenant_id` filter despite the column existing and being joined elsewhere — added
both, matching the existing `client_id`/`property_id` filter pattern exactly.
`contract_edit.js`/`payment_edit.js` also gained `tenantId` viewParam prefill (they
only supported `propertyId`/`clientId` before) so "Nuovo Contratto/Pagamento" from the
tenant scheda actually preselects the tenant.

Verified live: created a tenant reminder via `POST api/reminders.php` with
`tenant_id`, confirmed it round-tripped through `GET ?tenant_id=`, then deleted it.
Confirmed `contracts.php?tenant_id=70` and `payments.php?tenant_id=70` both return
real rows for an existing demo tenant.

**Known gap, not fixed (scope call):** a Comunicazioni tab was intentionally left out
— `communications.php` is `client_id`-only with no tenant equivalent, and building
one is a real feature addition, not a bug fix. The Documenti tab falls back to the
tenant's current property's documents (labeled honestly as such in the UI: "condivisi
con il proprietario e altri inquilini dello stesso immobile") since the `documents`
table has no `tenant_id` column.

Verified live: linked a real property to a building via `POST

unlinked to restore state.

## 5. Chiavi — card styling + form completeness

**Fixed.** Cards only showed detentore/stato/ubicazione with no way to tell which
*physical* key a row was about — the schema had no field for it, even though
multiple key rows per property were always possible (no unique constraint on
`property_id`). Added `key_type` (portone/appartamento/cantina/box/cancello/altro),
`quantity`, `key_code` (physical tag label) via new migration
`phase63_key_details.sql` (nullable/defaulted, backward compatible), wired through
`api/property_keys.php`, the registra/modifica form (now fieldset-sectioned), and the
card display (type icon, copie badge, monospace code tag).

Verified live: created a key record with `key_type=cantina, quantity=2,
key_code=A12-TEST`, confirmed it round-tripped, confirmed a pre-existing seed row
correctly defaulted to `key_type=altro, quantity=1` after the migration ran.

## 6. Contatori — what it does

**Audit only, no changes needed/requested.** A "contatore" isn't a first-class row —
it's an implicit `(property_id, meter_type)` pair inferred from a flat
`meter_readings` log (gas/electricity/water/heating). Consumption is computed
on-the-fly by diffing against the prior reading (`api/meter_readings.php:84-91`), not
stored. **No billing/tariff linkage at all** — it's a pure consumption journal, never
feeds invoices or expenses. Filters (property, type) work correctly.

**Dead code found:** `getMeterSummary()` (`?summary=1&property_id=`) has zero
frontend callers anywhere in the repo — fully orphaned endpoint.

## 7. Inventario — broken button + missing filters

**Fixed.** Root cause: the mandatory "Seleziona immobile" `<select>` (nothing renders
until you pick one) sat inside a plain `.toolbar`, which `filters.js`'s generic
reference-bar logic auto-detects and relocates into a collapsed "Filtri" popover —
correct behavior for a real *filter* (see meters.html, which has an "all properties"
default and works fine there), wrong for a *mandatory gate* that IS the page's only
control. Added a `data-no-filterbar` opt-out attribute (checked at the top of
`setupBar()` in `filters.js`) and applied it here. Also added the actually-missing
category and condition-minima filters, server-side (`api/inventory.php`) and wired
client-side.

Verified live: `view.php?name=inventory` now serves the markup with
`data-no-filterbar` present; `GET api/inventory.php?property_id=78&min_condition=4`
correctly returned only the matching item.

## 8. Valutazioni OMI form

**Audit only.** Confirmed 100% manual entry — no import/scrape/API call anywhere,
same reality as the "no free Immobiliare.it API" situation. The page's own copy
oversells this ("Stima automatica... da quotazioni OMI"). Concrete gaps found: (a)
no "stato di conservazione" dimension unlike real Agenzia Entrate OMI data, (b) the
DB unique key doesn't include `period`, so re-entering a value for a new semester
silently overwrites the old one instead of building history, (c) the estimate engine
never reads the property's own `condition`/`livello` to bias within the OMI range —
flat €/m² × sqm blend only, (d) the quick estimate on this page can't be saved (no
"save as valuation" button — that only exists on a *different*, unlinked page:
Immobili → calculator icon → `property_appraisals.php`). Also: the form is still flat
(no fieldset sections), which is inconsistent with the comparably-sized building
modal that *did* get sectioned in the same audit batch.

**Not fixed** — these are feature/data-model decisions (add a conservation-state
column, decide on history vs. overwrite, wire the estimate to property condition),
not bugs, and weren't asked for as fixes.

## 9. Contratto nuovo/modifica form

**Audit only.** Fieldset sectioning is genuinely done (5 real sections, verified
against `git show 62eb3e5`, not just the doc's claim). RLI/cedolare fields are
present and correctly scoped (this form only tracks registration references/
deadlines — no fake "submit to RLI" button, honest about the Agenzia Entrate portal
being the real filing point). "Genera scadenzario" idempotency is solid — a
`SELECT...FOR UPDATE` + existing-payments check inside a transaction, confirmed no
double-click can create duplicate rows. `tenantId` viewParam prefill (added this
session) is present and consistent with `propertyId`/`clientId`.

**Real gap found, not fixed:** no conditional fields — the "Registrazione e fisco"
block (cedolare secca, ISTAT baseline, RLI subtype) is always visible/editable
regardless of `contract_type`, so a compravendita or mandato can have cedolare secca
ticked, and neither the client JS nor `validateContractInput()` server-side stop it.
This is a real UX/data-integrity gap worth a follow-up, scoped as: hide/disable that
fieldset unless `contract_type === 'locazione'`, both sides.

## 10. Fatture — how it works

**Audit only, plus one bug fixed in passing.** Full lifecycle (draft→sent→paid→
cancelled) is real; VAT/total are MySQL `GENERATED` columns (immune to app bugs); PDF
generation is a genuine working hand-rolled PDF writer (`lib/SimplePdf.php`), not a
stub. FatturaPA XML generation is real and standalone-usable (structurally valid,
readiness-checked against agency settings) but **not digitally signed** and **not
transmitted** out of the box — `lib/sdi_sender.php` defaults to `SDI_PROVIDER=manual`
with no API key, so the button just says "download it, upload it yourself to your
accredited channel." Actual SdI transmission needs a real Aruba/Fatture-in-Cloud
account + API key + endpoint verification (the HTTP call itself is admitted
scaffolding, per its own inline comment). `fattura_transmissions` table only exists
via migration, not in the schema-dump baseline (recoverable since Docker's entrypoint
runs migrations on boot, but a manually-restored DB would miss it).

**Bug found and fixed:** the "segna come inviata/pagata" quick buttons sent a PUT
without `property_id`, silently wiping it every click since the API does a full-
column update (`invoices.js:quickStatus`). Fixed by including it in the payload.
Verified: `property_id` is present in the list query (`i.*`), so the fix is complete.

## 16. Gestione forms (manutenzione, assicurazioni, fornitori, richieste, antiriciclaggio)

**Audit for all 5; 2 concrete bugs fixed.**

- **Manutenzione:** two disconnected systems exist under one name — a rich
  `maintenance_requests` table that nothing ever writes to (dead), and the real
  workflow built on `reminders` (`maintenance_status`, `supplier_id`). Priority
  filtering is non-functional: the column is never written by any code path, so
  filtering by any priority value returns nothing. No cost tracking in the live
  system, no admin-initiated "new request" (only tenant-reported).
- **Assicurazioni — bug fixed:** `api/insurance.php`'s `INSURANCE_TYPES` whitelist
  still had the pre-migration 4 values; the DB enum was widened to 8 months ago but
  the PHP validator was never updated, so **saving 4 of the form's own 6 policy-type
  options failed server-side**. Fixed the whitelist to match the DB enum exactly, and
  restored `responsabilita`/`globale_fabbricato` as select options so legacy records
  don't show a blank dropdown when edited. Verified live: created a policy with
  `policy_type=furto` (previously rejected), confirmed success, deleted it.
- **Fornitori — same bug, same fix:** `SUPPLIER_CATEGORIES` rejected
  `giardinaggio`/`ascensore`/`serrature` (3 of the form's own options). Fixed
  identically; restored `imbianchino`/`giardiniere` as options. Verified live with
  `category=ascensore`.
- **Richieste immobili:** status workflow is clean and correctly matched everywhere.
  Found (not fixed) a real bug: the UI's "convert to lead" bypasses the server's own
  correct, transactional, idempotent `convert_lead` action and instead posts directly
  to `leads.php` with the wrong field name (the lead table doesn't even have
  `property_id`) and no `interest_type` — silently dropping the property link and
  allowing duplicate leads on repeat clicks. **This one I did fix** (see the
  Sondaggi/property_applications section below — it was cheap and clearly a bug, not
  a feature decision).
- **Antiriciclaggio:** the one of the five actually done to full standard —
  fieldset-sectioned, enums aligned everywhere, retention correctly wired into both
  the scadenzario feed and the GDPR-erasure override. One real gap: no way to link a
  check to a `lead` from the UI despite the column/API supporting it, and no PDF/
  print export of the compliance record (pure data entry for something that by law
  must be producible on request).

## 17. Comunicazioni + WhatsApp Inbox

**Audit only.** Both channels share one send/log path
(`api/communications.php`/`config/mail.php`/`config/whatsapp.php`): if `mail_enabled`/
`whatsapp_enabled` is false (confirmed false in this environment's `.env.docker` and
`app_settings` — no `TWILIO_*` or live SMTP creds reachable anywhere in this repo's
config surface), a simulated success is logged and nothing is actually sent. WhatsApp
Inbox's threading (client+tenant), template system, and outbound logging are
genuinely implemented, not decorative. Webhook signature validation
(`api/whatsapp_webhook.php`) reads as correctly fail-closed in production per direct
code inspection (HMAC-SHA1 + `hash_equals`, 503 if no token configured in prod) — **not
re-verified with a live unsigned curl POST this session**, so that's a code-read
confirmation, not an executed-request one.

**Verdict, unchanged from existing docs:** both are demo-only. Mail needs the
Mailgun/SMTP auth issue fixed and `mail_enabled=true` with a verified sending domain.
WhatsApp needs a paid, Meta-approved Twilio WhatsApp Business sender — the free
sandbox requires every single recipient to individually text "join &lt;word&gt;"
first, with no admin/bulk workaround, and it silently looks like it worked (API
returns success) while the message never arrives to anyone who hasn't opted in.

## 21. Automazioni

**Audit only.** What the page presents ("email programmate... in base alla frequenza
configurata") is exactly what it is — a thin, honest relabeling of the Reminders
system with `notify_client=1` forced; every `automations.js` call hits
`api/reminders.php` under the hood. There is no trigger/condition/rule engine here,
which may surprise a user expecting "automation" to mean something more dynamic.
The recurring-send execution loop (`cron/process_reminders.php`) is real (reschedules
correctly, logs to `communications`), and **is scheduled on Render**
(`render.yaml` has a real cron service, `*/15 * * * *`) but **not scheduled at all in
the local/Docker dev setup** — nothing in `docker-compose.yml`/`Dockerfile` ever
invokes it, so pending automations sit forever in dev unless run by hand.

Separately, `api/automations.php` — a more ambitious "automation rules" backend with
its own `automations` table (name/trigger/action/run_count) — is **entirely dead
code**: zero frontend references anywhere in the repo, nothing ever writes to that
table, and its own doc comment admits the table isn't wired up. The page you actually
click has nothing to do with this file.

## 22. Whole-project synthesis

Covered above, item by item. Additional things noticed along the way, not otherwise
filed:

- `api/property_applications.php`'s server-side `convert_lead` action is correct,
  transactional, and idempotent (409s on a second attempt) — but the frontend
  bypassed it entirely, posting to `leads.php` directly with the wrong field name
  (`property_id`, which `leads.php` doesn't have — the real column is
  `preferred_property_id`) and no `interest_type`, with no duplicate-conversion
  guard. **Fixed:** switched the frontend to call the real endpoint; the button
  now disables and relabels ("Già convertito (lead #N)") once converted. Verified
  live: converted a real application, confirmed a second attempt correctly 409s
  instead of creating a duplicate lead.
- `api/surveys.php`'s own `createSurvey()` builds its public link as
  `/survey.php` (root), but the actual file only exists at `tenant/survey.php` — the
  frontend already ignores this broken field and builds its own correct link
  client-side, so no user-visible bug, but the backend's `link` field in its API
  response is dead-wrong if anyone ever integrates against it directly. Left as-is
  (out of scope for what was asked; noting it here so it doesn't get "discovered"
  again later).
- `assets/js/property_applications.js` had a dead `LEADS_API` constant left over
  after the convert-to-lead fix — removed.
